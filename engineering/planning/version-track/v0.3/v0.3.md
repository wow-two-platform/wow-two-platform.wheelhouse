# v0.3 — Operations and secrets console

*Last updated: 2026-10-02*

**Status:** 🚧 In Progress · **Type:** Feature · **Started:** 2026-09-24 · **Completed:** —

### Iteration 1 — Deployment operations

- [x] Ability to see why a deployment was refused or failed, without exposing setting values.
- [x] Ability to print a service's settings skeleton from its release contract.
- [x] Fix health probes failing when a service restricts its allowed hosts.
- [x] Ability to see recent deployments with outcome, reason, actor and release after a reload.
- [x] Ability to check a target's readiness without changing it.
- [x] Ability to see the release each target runs and whether it is locked.
- [x] Ability to reconcile an interrupted or failed deployment from the dashboard.
- [x] Ability to rehearse deployments against a local SSH target.

### Iteration 2 — Workspace

- [x] Ability to operate a product from one workspace: product rail, environment, services and an inspector.
- [x] Ability to move between workspace, deployments, servers, secrets, products and activity from the top bar.
- [x] Ability to use a top bar that spans the full window, with the console version beside the name.
- [x] Ability to redeploy an earlier release from the deployment history.
- [x] Ability to reach sign-out and the API status from the profile menu in the top bar.
- [x] Ability to switch between light, dark and system themes from the profile menu, remembered per browser.
- [x] Ability to see the console and API versions, with the API's commit, from the profile menu.
- [x] Ability to sign in from a screen that shows only the name, one line and the GitHub action.
- [x] Ability to search products in a compact catalogue beside the selected product's details.
- [x] Ability to tell products apart by the icon each repository carries, or a tinted monogram.
- [x] Ability to open a product's repository, branch or commit on GitHub and copy its clone command.
- [x] Ability to read a product's registry identifiers from an info popover beside its name.
- [x] Ability to use every dialog inside the window: its body scrolls under a fixed header and footer.
- [x] Ability to deploy from a page header or a history row through one dialog: choose, confirm, follow.
- [x] Ability to see each deployment figure's change against the previous 30 days.
- [x] Ability to scan long lists with a pinned header, hover rows and status dots.
- [x] Ability to see a page's frame and labels at once, with only its values loading.
- [x] Ability to refresh a page and see only its values reload, never its layout.
- [x] Ability to refresh from one control on every page: its icon spins, its label stays, it dims.

### Iteration 3 — Secrets console

- [x] Ability to see each configured vault and whether it is sealed.
- [x] Ability to browse namespaces in a rail and secret metadata without revealing values.
- [x] Ability to create a namespace and to set or rotate a secret value.
- [x] Ability to disable and re-enable a secret.
- [x] Ability to mint a product token shown once, and to revoke tokens.

### Iteration 4 — Metrics dashboard

- [x] Ability to see each server's load, memory, disk and uptime without changing it.
- [x] Ability to see each target's containers with state, health, restarts, CPU and memory.
- [x] Ability to see 30-day deployment metrics: deploys per day, success rate, rollout time and recovery time.
- [x] Ability to see which targets run an older release than the latest published one.
- [x] Ability to see secrets and product tokens due for rotation.
- [x] Ability to see everything that needs attention across the portfolio on the servers page.
- [x] Ability to tell a manual vitals refresh ran: values turn into placeholders and back, even when unchanged.

### Iteration 5 — Local environment

- [x] Ability to run Wheelhouse in its production image against the local target and vault with one command.
- [x] Ability to deploy from the containerized console over SSH, as on a VPS.
- [x] Ability to run Wheelhouse from an IDE against the local rig, marked by a `Local rig` badge.
- [x] Ability to deploy Wheelhouse to the local server with its own release generator and runner.
- [ ] Ability to sign in to the local console through a localhost GitHub OAuth app.

### Iteration 6 — Environments

- [x] Ability to run a product's dev, test and prod environments on one host at once.
- [x] Ability to deploy any commit's build to dev, and only published releases to test and prod.
- [x] Ability to run dev on the local server by default and deploy test or prod there on demand.
- [x] Ability to deploy prod to the local server only after typing its target ID.
- [x] Ability to deploy to prod only a release that succeeded on test, or to skip that by typing the target ID.

### Iteration 7 — Sites

- [x] Ability for a product to declare which services and ports serve public or private sites.
- [x] Ability to open each environment's sites from Wheelhouse, including right after a deploy.
- [x] Ability to reach every local environment's sites at `*.localhost` addresses.

### Iteration 8 — Builds

- [x] Ability to describe a product's services, builds and change paths in one `deploy.yml`.
- [x] Ability to build only the services a commit changed, each keeping the version it last changed in.
- [x] Ability to see each service's version on a target.
- [x] Ability to start a build for a commit that has none.
- [x] Ability to open any listed commit on GitHub, and to see why a build was refused.
- [x] Ability to browse the release catalog and deploy a release from it.
- [x] Ability to build ForeverPin commits from its own `deploy.yml` and workflow.

### Iteration 9 — Deployment visibility

- [x] Ability to follow each step of a rollout while it runs, and to review the steps afterwards.
- [x] Ability to see whether each site answered through the ingress right after a deploy.
- [x] Ability to read a service's recent container output from Wheelhouse.
- [x] Ability to check that a target's ingress answers before deploying.
- [x] Ability to keep a target's disk from filling with images of old releases.
- [x] Fix smoke checks for services that listen on a port other than 8080.

### Iteration 10 — Audit

- [x] Ability to see who deployed, reconciled, built, changed a secret or edited a product, and when.
- [x] Ability to tell whether an audit entry was edited or removed after it was written.

### Iteration 11 — Continuous integration

- [x] Ability to run every test tier on each push.
- [x] Ability to build Wheelhouse's own images and release bundles from a commit or a release.
- [x] Ability to version every build from the version track and publish it through the shared pipeline.

### Iteration 12 — Service map

- [x] Ability to see a target's Compose services, networks, volumes and startup order as a map or a list.
- [x] Ability to see each service's observed container state on the map, separate from its declaration.
- [x] Ability to see each service's sites, platform needs and version on the service map.
- [x] Ability to pan and zoom the service map by drag, wheel, pinch, keys and controls.
- [x] Ability to see every service's version on the map, or the release it runs when none is recorded.
- [x] Ability to compare a product's environments service by service and promote a release to the next one.

### Iteration 13 — Operations history

- [x] Ability to see each host's load, memory and disk trends over the last day, week or month.

### Iteration 14 — Brand

- [x] Ability to recognize Wheelhouse by its wordmark in the top bar and on sign-in, and by its boat in the browser tab.
- [x] Ability to see the Wheelhouse wordmark and the load progress while the console starts.

### Iteration 15 — Conventions

- [x] Split the frontend into a pnpm workspace with the app in `apps/web`.
- [x] Refactor the backend onto central package versions, a pinned SDK band and shared build properties.
- [x] Refactor cross-slice imports onto each slice's own barrel.

### Iteration 16 — Product catalog

- [x] Ability to see each product as the code-owned catalog defines it: name, description, repository and environments.
- [x] Ability to see each environment's sites and vault namespace beside its product.
- [x] Ability to record a product's lifecycle: idea, building, live, paused or killed.
- [x] Ability for another program to read the catalog at `/api/products` with a scoped integration key.
- [x] Ability to create an integration key shown once, see its last use, and revoke it.
- [x] Ability to list the branches and commits of any catalog product, with or without a release source.
- [x] Refactor the backend onto SDK `10.0.62-beta`: camelCase enums, API key scopes, no package advisories.

### Iteration 17 — Inventory in the database

- [x] Ability to add, edit and delete products with their release source; the slug is fixed once created.
- [x] Ability to add, edit and remove a product's environments: server, settings files, smoke checks and site hosts.
- [x] Ability to add, edit and delete servers with their ingress, and the vaults that run on them.
- [x] Refactor the runner onto the API-exported `inventory.json`; a malformed snapshot is refused whole.
- [x] Refactor the backend onto SDK `10.0.63-beta` and the console onto UI SDK `0.0.12`; local SDK copies deleted.

### Iteration 18 — Verification

- [ ] Deploy a release to the local target → history shows the outcome after a reload.
- [ ] Blank a required setting → the check names the key; a deploy changes nothing.
- [ ] Interrupt a rollout → reconciling from the dashboard unlocks the target.
- [ ] Set a secret in the console → a product token reads the new version.
- [ ] Run `rehearse.py run` → the dev site opens at `http://app-foreverpin.dev.localhost:18080`.
- [ ] Deploy a release to test beside dev → both sites answer at once, each on its own host.
- [ ] Deploy to local prod without typing its ID → refused; typed → deployed.
- [ ] Choose a commit build for test → refused before anything reaches the target.
- [ ] Deploy an untested release to prod → refused; skipping with the typed ID → deployed.
- [ ] Build a commit without a build → its workflow starts; a built commit offers Use build.
- [ ] Stop a container on the local target → the fleet page shows it stopped and the overview flags it.
- [ ] Deploy a broken release → the overview's failure count and success rate change.
- [ ] Open the secrets page → each secret and token shows its age; overdue ones are flagged.
- [ ] Run `rehearse.py console`, sign in with GitHub and open every page → each page loads without errors.
- [ ] Deploy to dev → the dialog lists each step as it runs; the workspace inspector shows them after a reload.
- [ ] Stop the local ingress and deploy → the deploy succeeds with a warning, and the site link flags it.
- [ ] Check a target with the ingress stopped → the check names the ingress.
- [ ] Open a service in the workspace → Read logs shows its latest lines; Refresh reads them again.
- [ ] Deploy, then change a secret → Activity lists both with the operator, and the chain shows intact.
- [ ] Push to GitHub → `ci` runs all three jobs; `publish-docker-image` uploads `bundle-<sha>`.
- [ ] Push to `main` → the shared workflow releases `v0.3.Z`, and the top bar shows that version.
- [ ] Open dev's service map → each site links out with its answer state, and `postgres` shows as a platform service.
- [ ] Deploy a release to test only → Environments highlights what prod lacks and offers the promotion to prod.
- [ ] Open Deployments → Releases lists releases and commit builds; its Deploy button opens the dialog with it chosen.
- [ ] Leave Wheelhouse running for an hour → the Fleet page draws load, memory and disk lines for each server.
- [ ] Run `rehearse.py self` → Wheelhouse's console answers at `http://console-wheelhouse.dev.localhost:18080`.
- [ ] Open the workspace → the product rail selects a product; the inspector follows the selected service.
- [ ] Open a service map → the controls, Ctrl + scroll and a pinch zoom it; a drag pans; a click still selects.
- [ ] Open the profile menu → it shows the console version and the API version with its commit.
- [ ] Sign out → the sign-in screen shows only the name, one line and the GitHub button.
- [ ] Show scroll bars always (macOS setting) → the top bar still reaches the window's right edge.
- [ ] Open Secrets → its frame, tabs and table headers show at once; only values load.
- [ ] Refresh Secrets → statuses, counts and versions flash; vault, namespace and key names stay.
- [ ] Open an old `/fleet` link → it lands on Servers with the same product selected.
- [ ] Open Deploy a commit on a short window → the dialog fits and its commit list scrolls.
- [ ] Click a commit's short SHA → GitHub opens that exact commit.
- [ ] Build a commit of a product without a build workflow → no Build button; the note says why.
- [ ] Choose a branch in a product's repository menu → the link and the clone command follow it.
- [ ] Open Products → each product shows its repository icon, or a tinted letter when it has none.
- [ ] Open the console on a slow session read → the wordmark and bar show at once and fill, then the page appears.
- [ ] Switch to dark → the top bar and sign-in show the white wordmark; the tab shows the white boat.
- [ ] Run `pnpm install && pnpm dev` in the frontend workspace → the console serves at `https://localhost:5174`.
- [ ] Open Products → each product shows its environments, their sites and vault namespaces.
- [ ] Set a product's lifecycle → Products and the workspace show it after a reload; Activity records it.
- [ ] Create an integration key → it shows once; `curl` with it reads `/api/products` but gets 401 from `/api/deployments/targets`.
- [ ] Revoke the key → the same read gets 401; the key list shows it revoked, with its last use.
- [ ] Add a product with a dev environment on the local server → the runner lists its target after the save.
- [ ] Delete a product an environment still uses → refused with the reason; remove the environment → deleted.
- [ ] Add a server without its `ssh/<slug>/` files → saved; a check on its target names the missing identity.
- [ ] Restart `rehearse.py console` → the local server, its targets and vault return; operator products stay.
