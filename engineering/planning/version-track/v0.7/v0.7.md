Spec: `wow-two-ws/ideas/migrations-analysis-2026-10/migrations-spec.md` § 3.4 and § 4 phases 3-4, which supersede the
Identity chat's step spec; built on be sdk `10.0.93-beta`'s verb tree and pipelines `v0.12.0`. Identity's first
deployment waits for this step. How it runs: [deployment.md § Migrate step](../../../deployment/deployment.md#migrate-step)
and [§ Wheelhouse migrates itself](../../../deployment/deployment.md#wheelhouse-migrates-itself).

Bridge, one release instead of the spec's two: prod's console deploys each Wheelhouse release to dev and promotes it to
prod with its own runner (`transport.submit` uploads it), so while prod runs v0.7.5 no console rollout of Wheelhouse
runs a migrate step; `self-deploy.py` and CI's fallback run the release's own runner, which has it. The release adds no
migration and v0.7.5 and v0.7.7 both stop at `034`, so it boots read-only on either database whichever runner deploys
it; where the step runs it applies nothing and records the history's kinds. Boot apply therefore goes now, and the rule
moves to the first release that adds a migration: it ships only once prod runs v0.7.7 or later, since a runner without
the step leaves it refusing to boot and restoring the previous release, nothing applied. Proven on PostgreSQL 18:
v0.7.7 migrated a database, the new image checked and stepped it, v0.7.7 booted on the upgraded history again.
