### Iteration 1 — A secret linked across products

events-integration #22: Events calls SCFD as Ocharo Identity's client `events`, whose secret is generated on
`ocharo-dev` and must reach `events-dev` unchanged; `from` stays inside one product and the vault never shows a value.

- [x] Ability to link a target's key to another product's key in the same environment, and to unlink it
- [x] Ability to render a linked key from its source's current value: a vault secret's version, a stored setting
- [x] Ability to read a linked key's source, secrecy, version and fingerprint in the environment's settings, and to see
  it unapplied after its source changes
- [x] Refuse a link across environments, within one product, to a linked key, to or from a derived key, or onto a key
  the release links; refuse a value saved to a linked key
- [x] Ability to link and unlink a key from the environment's settings in the console

### Iteration 3 — What the live sweep found

The live sweep of Ocharo's dev targets (events-integration, 2026-11-10) and today's two Identity config-check refusals
(`ocharo-dev` `v0.3.0`, `v0.3.2`: keys typed ahead of their release reached every service).

- [x] Hold a key no service of the release declares from every service until a release that declares it deploys: a
  stored value, a vault secret, or a key the owner added unless added for every service (`every_service`, off for the
  six keys typed ahead on Ocharo); the plan marks it `held` ("held until a release declares it" in the editors), and a
  held key never counts as missing. A release that declares no service holds nothing (`v0.15.1`)
- [x] Ability to give a newer release's required key from its refusal, and reach the deploy dialog's settings step
  without Check readiness: a deploy refused only for missing required settings offers "Fill in settings" (the page's
  action, and a button under its cause; `?fill=settings` opens it from a link), which opens the dialog on that target
  and release at its confirm step; the confirm step shows "Reading the release's settings…" while the plan loads,
  where it showed nothing before and read as a skipped step (`v0.15.2`)
- [x] Keep a run's whole last line when it is structured output, and the lines before it: the last line whole up to
  16 KiB (`ocharo setup`'s JSON, a 12 KB `import-report`), and `tail`, the last 20 lines before it scrubbed the same
  way within 32 KiB in all, for a run that succeeded or failed; the Run dialog shows them under "Earlier output"
  (`v0.15.3`)
- [x] Ability to hand a one-off run a file on its stdin: the Run dialog's "Stdin file" (2 MiB at most) goes base64
  beside the command on each stdin hop (API, transport, target worker) into `docker run --interactive`, written nowhere;
  the job keeps its size and SHA-256 (`run.input`), the audit its size (`v0.15.3`)
