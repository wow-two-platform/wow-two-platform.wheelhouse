# Wheelhouse — Frontend Development Guidelines

*Last updated: 2026-10-17*

Shared frontend conventions live in `wow-two-ws/conventions/development/frontend/`.
This document records Wheelhouse-specific choices; the workspace design is in
[architecture](../architecture/architecture.md#workspace).

## Stack

- Vue 3 Composition API · Vue Router · Vite 6 · TypeScript (strict) · Tailwind v4 · Node 24 · pnpm workspace.
- UI: the published fe sdk **`@wow-two-beta/fe@0.0.20`**. Use its components, forms, queries and Result contracts. Shared capability gaps belong in the SDK; product composition stays here.
- `bootstrap/index.css` imports `tailwindcss` and `@wow-two-beta/fe/styles.css`; its `@source` includes SDK utilities.
- `bootstrap/query.ts` and `bootstrap/form.ts` are the application adapter pins. Integration functions decode wire payloads with Zod and return SDK `Result<T, ApiFailure>` values.

## Conventions

- One app, `apps/web` (`@wheelhouse/web`), in the pnpm workspace at `engineering/codebase/wheelhouse.frontend-services/`. API client is same-origin (`/api/...`); HTTPS dev server `:5174` proxies to HTTPS backend `:8210` (see `apps/web/vite.config.ts`); `pnpm dev:http` serves plain HTTP for headless previews. Preserve secure cookies and forwarded origin during GitHub authentication.
- Production: `pnpm deploy` (`scripts/deploy.mjs`) builds the app and copies `apps/web/dist/` into the API's `wwwroot` (single-host serving). Idempotent — `wwwroot` is wiped + repopulated each run.
- `pnpm typecheck` runs `vue-tsc` and the SFC compiler gate. `pnpm test` (`apps/web/tests/console/`) checks routing and redirects, product selection, the status filter, pin ordering, catalog selection, API decoding, sensitive-form lifecycles and the deployment history rules (calendar colour and intensity, the entity picker's selection model, filter address round trip). `pnpm build` includes typechecking and lazy route bundling.

## Button sizes

Controls that sit together share one height; the row's place sets it.

- **`md` (40px):** the top bar (page actions through `PageHeaderActions`, the sidebar toggle, the profile trigger), dialog and sheet footers, a panel's full-width action, and any row that holds a picker or a segmented control. Every `SelectPicker` trigger is `md`; a segmented `ToggleGroup` takes `sm` items, whose track stands 40px tall.
- **`sm` (32px):** every other row inside a panel, card, table or list: row and card actions, panel-header buttons, toolbars without a picker, actions inside an alert or empty block, paging.
- **Phones (below `md`):** a row that grows to the 44px touch target grows whole: labelled buttons and triggers `max-md:min-h-11`, icon-only buttons `max-md:size-11`, segmented items `max-md:min-h-9` (a 44px track). The top bar and dialog footers stay at 40px.
- **Icon-only buttons** take `shape="square"` at their row's size; `RefreshButton icon-only` does this itself.
- **Destructive actions** keep `tone="danger"` and their row's size: `DeleteConfirm` is `md` in a dialog footer, where it sits on the left with Cancel and the primary on the right, and `size="sm"` in a list row.

## Repo-specific deltas

- Control-plane workspace only — single operator, never public. Secret writes and token minting bypass the mutation cache. Plaintext stays inside the active dialog; abort/generation guards prevent dismissed requests restoring it. Failed writes preserve editable input; successful writes and context changes clear values and form baselines.
- The console's first load: `index.html` paints a static splash (`public/boot-splash.css`) that mounting replaces with `BootSplash`, the SDK `SplashScreen` overlay on the ambient surface; its bar reports scripts, session and first route (35, 70, 100). Keep the two in step.
- Each panel loads inside an fe sdk `DataRegion`: a first load renders the real layout over `useSkeletonItems` placeholders and every SDK component inside draws its own skeleton; explicit refresh uses the local `useRefresh` timing helper. A failed refresh keeps the last good content, and query failures reach the toast host.
- A page's primary action goes in the shared header through the SDK `PageHeaderActions`; the page owns the dialog.
- Colours come from the fe sdk `platform` theme (`theme-platform` on `<html>`, `surface-ambient` backdrop); `bootstrap/index.css` keeps only app tokens the theme lacks (charts, sidebar, glass, map). Vite generates `/theme.js` from the SDK `colorModeScript`, which applies the remembered scheme before the first paint.
- Entities nest Workspace → Product → Service; deployments cut across services, and a server hosts many products. Primary navigation on every class is Home · Products · Deployments · Servers (`application/navigation/PrimaryNavigation.ts`; Products covers `/products`, `/w/…` and `/p/…`). Routes: `/` Home (attention, pins, every workspace's product cards); `/products` the products browser (workspace chips — All, then each workspace — over product cards; New product, Workspaces and each card's Edit are its actions) and `/w/:workspace` the same page narrowed to one workspace; `/p/:product/:tab?…` a product page; `/deployments` and `/deployments/:id` one deployment; `/servers`. `/activity` and `/secrets` are the portfolio-wide views the profile menu opens; `/settings/keys`, `/settings/catalog`. An old Workspace link `/?product=x&target=…` redirects to `/p/x?target=…`, and the product page rewrites the target as its `env`.
- Frame (`bootstrap/AppLayout.vue` on the SDK `AppShell`): desktop (≥1024px) a 248px sidebar (`presentation/shell/ConsoleNav` on the SDK `SidebarMenu`) that collapses to a 64px icon rail, remembered in `localStorage`. Sidebar, rail and tablet drawer share one order: Home, Products, Deployments, Servers (no heading; `PrimaryDestinations.ts`), then Pinned (badged in the rail), then Workspaces — each a row whose name opens `/w/:workspace` and whose chevron folds its products, remembered per workspace. Tablet: the rail, with the full sidebar in a left `Drawer`; phone (<768px) no sidebar and the SDK `BottomNavMenu` in the shell's footer row with the same four destinations, so the scrolling region ends above it. Everything else — Activity, Secrets, Integration keys, Catalog, "Show inactive", appearance, sign-out — sits in the profile menu (`ProfileMenu`, the avatar ending the top bar): a `DropdownMenu` from `md`, a `BottomSheet` (`ProfileSheet`) on phones; its trigger is the SDK neutral outline `Button` at `md`, matching the top bar's other buttons (square on phones, where it holds the avatar alone). The top bar (`ScopeBar`) shows the scope trail (Home › Workspace › Product › Service, or › Tab on a product tab; phones keep the last two steps) and holds the page's `PageHeaderActions`; the page heading is the current crumb, for assistive technology.
- The product page (`presentation/product/ProductPage.vue`) carries one product: a header (`ProductHeader`: workspace chip, homepage, pin, Active switch, repository and the Manage menu — edit product, refresh from repository, add or edit environments) over tabs, each at its own address: Overview `/p/:product` (environment surface, comparison, services map/list, recent deployments, inspector beside them from `xl`), Releases `/p/:product/releases` (the product's `ReleaseCatalogPanel`), Secrets (the environment's vault namespace through the Secrets page's tables; a missing namespace is one click away) and Activity (`AuditEntriesPanel` over `/api/audit?product=`), then Deployments `/p/:product/deployments` (the Deployments page's `DeploymentsPanel` with its entity filter locked to the product). A tab is an entry in `ProductTabs` (`application/navigation`) plus a `TabsGroupPanel` in the page; only the chosen panel renders, and it contributes its own top-bar actions. The tab list scrolls sideways on phones; an unknown tab falls back to Overview. The environment segmented control sits in the top bar on Overview and Secrets (`?env=`). Invalid explicit selections remain unavailable rather than silently selecting another target; without `env`, the environment last chosen on any product page applies when the product has it.
- Products and services are active or inactive; inactive ones stay hidden everywhere until the one "Show inactive" switch (profile menu) is on. Pins (workspaces, products, services) list in custom order in the sidebar and on Home; a pinned service opens in the environment last chosen. Status, pin and order writes are optimistic (`useOptimisticMutation`) and roll back on refusal.
- View choices live in `localStorage` through `application/preferences` (`wheelhouse.show-inactive`, `wheelhouse.sidebar-collapsed`, `wheelhouse.sidebar-collapsed-workspaces`, `wheelhouse.environment`), every access wrapped so blocked storage only loses the choice. Icon addresses the host answered not found are remembered for 12 hours (`wheelhouse.missing-icons`, `application/products/IconAvailability.ts`), so each mark falls back to its tinted letter without asking again; Refresh from repository forgets a product's entries.
- First load: every page is a lazy route chunk; Vue with its router and the query cache with zod ship as `vendor-vue` and `vendor-data` chunks beside the entry (`vite.config.ts`). Shell parts a first visit rarely needs load on first use — the phone's profile sheet, the tablet's drawer and the pin editor — as do the product page's tabs other than Overview, and barrels that carry heavy modules (`presentation/products` without `RepositoryActions`, `presentation/pins` without `PinEditor`) are bypassed by path in the shell.
- Registry/runner association uses explicit bindings in `application/product/ProductInventory.ts`. Product status, observed runtime condition and deployment outcome remain separate facts; per-environment health on product cards comes from `domain/overview/EnvironmentHealth.ts` over the targets, vitals, stats and history the console already reads.
- Servers list the products each hosts (`hostedProductsOf`, from the targets) and lead with degraded ones: a server that cannot be read, is overloaded, short on memory or nearly out of disk (`AttentionRules.ofServer`) names what is wrong and the products it affects, each linking to its page. A vault row opens the Secrets page on that vault (`vaultLocation`).
- Host vitals are current snapshots that the SDK query refetches every 60 seconds; each server's host history comes from the backend sampler, which keeps samples for its retention window. Deployment follow-up refetches every three seconds while the tab is visible.
- The Deployments page, top to bottom: Issues (`IssuesPanel` over `/api/deployments/issues`: each target whose latest rollout failed, rolled back, failed to roll back or was interrupted with no success since, and each rollout stuck over 30 minutes — product, environment, release, what happened, when and by which actor; Open, Redeploy, or Reconcile where the target is likely locked, which first reads the target's state and opens `ReconcileModal` on the remote rollout it reports; read every minute while visible; absent when there is none), Running now (live rollouts, their step and a ticking elapsed time; read every three seconds while visible, absent when nothing runs; a rollout leaving the list refreshes the history views) and Ready to promote (one Promote per product opens the deploy dialog on its prod target and release; inactive products hidden; absent when nothing waits), all three portfolio-wide whatever the filter; then the filter (`DeploymentFilterScope`: the page's one `DeploymentFilterBar` in a glass strip that sticks under the top bar and says it applies to what lies below), the four measures (`RangeStatsTiles`: deploys, success rate, median rollout and recovery against the range before; entities and range, not status), and `DeploymentsPanel`, which holds a filter bar of its own only on a product's Deployments tab. The filter bar: `EntityPicker` (a Workspace → Product → Service checkbox tree, mix and match, summarized as chips; `domain/deployments/history/EntitySelection.ts`), All / Succeeded / Failed, and `DateRangeFilter` (24 h to 12 months, or custom local from/to); both pickers are popovers from `md` and bottom sheets on phones. Filter, view and expanded day live in the query (`workspace`, `product`, `service`, `status`, `range` or `from`+`to`, `view=list`, `day`; `application/deployments/DeploymentFilterQuery.ts`), defaults left out. Grid (`ActivityGrid`, rules in `ActivityCalendar.ts`): week columns × Monday-first weekday rows over the range (six months by default), fixed 20px cells with 4px gaps (22px with 3px gaps on phones), the calendar only as wide as its weeks, green all succeeded, red all failed, amber mixed, four fill steps (1, 2–3, 4–6, 7+), an inner mark on failed and mixed days, one shared tooltip drawn in the top layer (teleported to `body`) and kept inside the viewport — above its cell, below at the top edge, slid in at the sides (`HintPlacement`) — so no panel or screen edge clips it, and an aria-label per day, arrow keys between days, today in a dashed ring of the muted foreground tone (pulsing while a rollout runs, still under reduced motion) and the chosen day in a solid primary ring set off from the cell — chosen today keeps the solid ring and adds a small today dot; the legend names both; the line under it reads `N deployments · X succeeded · Y failed`, adding `· Z running` only while any run (a filtered view: `N deployments failed`; `ActivityCalendar.summary`); phones scroll it sideways from the newest weeks with sticky weekday labels. From `lg`, when the panel has room beside the calendar (`SidePanelRoom`, measured), a day panel sits to its right: the chosen day's deployments (`DeploymentList` in its compact `rows` layout) or, with no day chosen, the range at a glance (`DeploymentRangeSummary`: deployments, succeeded, failed and running, and the busiest products, each opening the product's Deployments tab). Narrower, a chosen day stacks beneath the calendar (`DeploymentList`, the List view's table, stacked into cards below `md`); cursor pages behind Load older either way. `/deployments/:id` (`DeploymentDetailPage`) shows the header, status and times, rollout steps (followed live while pending), services from → to with per-service logs, sites with probe results, failures and warnings, and Redeploy, Roll back (when `rollback` is offered), Reconcile (when the target needs it) and Read logs.
- Deployments submit approved target/release IDs. Reconciliation submits the authoritative remote active rollout ID and requires exact typed target confirmation. API action headers remain explicit.
- Clearing authentication invalidates the query session and HTTP request scope, preventing previous-session responses entering a replacement session.
