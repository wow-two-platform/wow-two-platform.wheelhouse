# Wheelhouse — Frontend Development Guidelines

*Last updated: 2026-10-19*

Shared frontend conventions live in `wow-two-ws/conventions/development/frontend/`.
This document records Wheelhouse-specific choices; the workspace design is in
[architecture](../architecture/architecture.md#workspace).

## Stack

- Vue 3 Composition API · Vue Router · Vite 6 · TypeScript (strict) · Tailwind v4 · Node 24 · pnpm workspace.
- UI: the published fe sdk **`@wow-two-beta/fe@0.0.30`**. Use its components, forms, queries and Result contracts. Shared capability gaps belong in the SDK; product composition stays here.
- `bootstrap/index.css` imports `tailwindcss` and `@wow-two-beta/fe/styles.css`; its `@source` includes SDK utilities.
- `bootstrap/query.ts` and `bootstrap/form.ts` are the application adapter pins. Integration functions decode wire payloads with Zod and return SDK `Result<T, ApiFailure>` values.

## Conventions

- One app, `apps/web` (`@wheelhouse/web`), in the pnpm workspace at `engineering/codebase/wheelhouse.frontend-services/`. API client is same-origin (`/api/...`); HTTPS dev server `:5174` proxies to HTTPS backend `:8210` (see `apps/web/vite.config.ts`); `pnpm dev:http` serves plain HTTP for headless previews. Preserve secure cookies and forwarded origin during GitHub authentication.
- Production: `pnpm deploy` (`scripts/deploy.mjs`) builds the app and copies `apps/web/dist/` into the API's `wwwroot` (single-host serving). Idempotent — `wwwroot` is wiped + repopulated each run.
- `pnpm typecheck` runs `vue-tsc` and the SFC compiler gate. `pnpm test` (`apps/web/tests/console/`) checks routing and redirects, session expiry (parallel 401s sign out once without error toasts, sign-in returns to the page), product selection, the status filter, pin ordering, catalog selection, API decoding, sensitive-form lifecycles, the Products page's rules (environment pills, the filter's address round trip with its date range, sorts, workspace figures and their range columns, the trend weeks a range covers, site links, where Products leads, the sidebar's product trail) the deployment history rules (calendar colour and intensity, mixed days while every attempt shows, the entity picker's selection model, filter address round trip with an old `status` ignored, the latest-of-day and every-attempt reads), the status vocabulary (each deployment's state, sub-state, attention and cause, the chosen day's counts, its product rows' lanes, bars and order, the release link a glyph opens, service strips, the impact list, the steps' changes boundary, mixed pills and their corner marker) and catalog workspace grouping. `pnpm build` includes typechecking and lazy route bundling.

## Button sizes

Controls that sit together share one height; the row's place sets it.

- **`md` (40px):** the top bar (page actions through `PageHeaderActions`, the sidebar toggle, the profile trigger), dialog and sheet footers, a panel's full-width action, and any row that holds a picker or a segmented control. Every `SelectPicker` trigger is `md`; a segmented `ToggleGroup` takes `sm` items, whose track stands 40px tall.
- **`sm` (32px):** every other row inside a panel, card, table or list: row and card actions, panel-header buttons, toolbars without a picker, actions inside an alert or empty block, paging.
- **Phones (below `md`):** a row that grows to the 44px touch target grows whole: labelled buttons and triggers `max-md:min-h-11`, icon-only buttons `max-md:size-11`, segmented items `max-md:min-h-9` (a 44px track). The top bar and dialog footers stay at 40px.
- **Icon-only buttons** take `shape="square"` at their row's size; `RefreshButton icon-only` does this itself.
- **Destructive actions** keep `tone="danger"` and their row's size: `DeleteConfirm` is `md` in a dialog footer, where it sits on the left with Cancel and the primary on the right, and `size="sm"` in a list row.

## Repo-specific deltas

- Control-plane workspace only — single owner, never public. Secret writes and token minting bypass the mutation cache. Plaintext stays inside the active dialog; abort/generation guards prevent dismissed requests restoring it. Failed writes preserve editable input; successful writes and context changes clear values and form baselines.
- The console's first load: `index.html` paints a static splash (`public/boot-splash.css`) that mounting replaces with `BootSplash`, the SDK `SplashScreen` overlay on the ambient surface; its bar reports scripts, session and first route (35, 70, 100). Keep the two in step.
- Each panel loads inside an fe sdk `DataRegion`: a first load renders the real layout over `useSkeletonItems` placeholders and every SDK component inside draws its own skeleton; explicit refresh uses the local `useRefresh` timing helper. A failed refresh keeps the last good content, and query failures reach the toast host.
- A page's primary action goes in the shared header through the SDK `PageHeaderActions`; the page owns the dialog.
- Colours come from the fe sdk `platform` theme (`theme-platform` on `<html>`, `surface-ambient` backdrop); `bootstrap/index.css` keeps only app tokens the theme lacks (charts, sidebar, glass, map). Vite generates `/theme.js` from the SDK `colorModeScript`, which applies the remembered scheme before the first paint.
- Entities nest Workspace → Product → Service; deployments cut across services, and a server hosts many products. Primary navigation on every class is Home · Products · Deployments · Servers (`application/navigation/PrimaryNavigation.ts`; Products covers `/products`, `/w/…` and `/p/…`). Routes: `/` Home (attention, every workspace's product cards; pins only on phones); `/products` the Products page (below); workspaces have no page — `#workspace-{slug}` on `/products` scrolls to a workspace's group, and an old `/w/:workspace` link redirects there; `/p/:product/:tab?…` a product page; `/deployments` and `/deployments/:id` one deployment; `/servers`. `/activity` and `/secrets` are the portfolio-wide views the profile menu opens; `/settings/keys`, `/settings/catalog`. An old Workspace link `/?product=x&target=…` redirects to `/p/x?target=…`, and the product page rewrites the target as its `env`.
- Frame (`bootstrap/AppLayout.vue` on the SDK `AppShell`): desktop (≥1024px) a 248px sidebar (`presentation/shell/ConsoleNav` on the SDK `SidebarMenu`) that collapses to a 64px icon rail, remembered in `localStorage`. Sidebar, rail and tablet drawer share one order: the main menu Home, Products, Deployments, Servers (no heading; `PrimaryDestinations.ts`), then a divider and Pinned (`PinnedNav`): the pinned products in custom order, each its icon, its name and a status mark only when its latest rollouts need the owner (red failing, amber degraded, blue deploying; `useNavConditions`, from the portfolio summary alone, so the always-visible sidebar never polls host vitals), Reorder pins editing the order in place. While a product page is open, Products unfolds to its Workspace › Product like a breadcrumb (`ProductsNavItem`, `productTrailOf`): the workspace opens the Products page at that workspace's group (`#workspace-{slug}`), and the product row is the current place; on any other page Products has no children, and there is no workspace tree. The Products row leads back to the product page last opened (and its tab) from outside Products, and up to the grid from inside it (`productsDestination`, `useProductsTarget`). The rail keeps the order as icons: Products, the open product's workspace and product grouped on a quiet ground under it, the four destinations, then a divider and each pinned product with its status badge. Tablet: the rail, with the full sidebar in a left `Drawer`; phone (<768px) no sidebar and the SDK `BottomNavMenu` in the shell's footer row with the same four destinations, so the scrolling region ends above it; its Products tab returns to the product last opened the same way, and the product page starts with an All products link on phones. Everything else — Activity, Secrets, Integration keys, Catalog, "Show inactive", appearance, sign-out — sits in the profile menu (`ProfileMenu`, the avatar ending the top bar): a `DropdownMenu` from `md`, a `BottomSheet` (`ProfileSheet`) on phones; its trigger is the SDK neutral outline `Button` at `md`, matching the top bar's other buttons (square on phones, where it holds the avatar alone). The top bar (`ScopeBar`) shows the scope trail (Home › Workspace › Product › Service, or › Tab on a product tab; phones keep the last two steps) and holds the page's `PageHeaderActions`; the page heading is the current crumb, for assistive technology.
- The product page (`presentation/product/ProductPage.vue`) carries one product: a header (`ProductHeader`) — the identity block (mark, name with an Inactive badge, a two-line description, the workspace chip opening its group on the Products page) beside one row of same-height `sm` actions: Open site (`OpenSiteMenu`), the pin, and Manage (`ProductManageMenu`: Active, edit product, refresh from repository, add or edit environments, the repository and Clone…, which opens `CloneModal` with its formats, branches and commits); on phones the mark shrinks and the actions turn to 44px icons beside the name so the tabs stay above the fold — over tabs, each at its own address: Overview `/p/:product` (environment surface — the verified release and deployment state, no site links, since the header's Open site holds them, and no per-service version pills, the comparison shows versions —, comparison — `EnvironmentCompare`: every version in the same outlined pill, one not yet in the next environment tinted, the column heads' releases in their own case —, builds — `BuildUsagePanel`: Actions minutes over 30 days and the average per run from `GET /api/deployments/products/{p}/usage` — services map/list with its own refresh and no release line, since each service may run its own version, recent deployments wearing the state chip the history reads for them — the product's history, every attempt, so a release whose dev check failed reads amber here as in the day panel — with View all opening the product's Deployments tab, inspector beside them from `xl`), Deployments `/p/:product/deployments` (the Deployments page's `DeploymentsPanel` with its entity filter locked to the product, then the product's `ReleaseCatalogPanel`, "Releases and builds", which deploys from its rows; the old `/p/:product/releases` redirects here with its query, so a `?release=&env=` link still opens), Secrets (the environment's vault namespace through the Secrets page's tables; a missing namespace is one click away) and Activity (`AuditEntriesPanel` over `/api/audit?product=`). Releases joined Deployments on 2026-10-19 (decision 43): "release" names a version, never the tab. A tab is an entry in `ProductTabs` (`application/navigation`) plus a `TabsGroupPanel` in the page; only the chosen panel renders, and it contributes its own top-bar actions. The tab list scrolls sideways on phones; an unknown tab falls back to Overview. The environment segmented control sits in the top bar on Overview and Secrets (`?env=`). Invalid explicit selections remain unavailable rather than silently selecting another target; without `env`, the environment last chosen on any product page applies when the product has it.
- Products and services are active or inactive; inactive ones stay hidden everywhere until the one "Show inactive" switch (profile menu) is on. Pins are products only (2026-10-18; the host refuses workspace and service pins and migration `015` converted them) and list in custom order in the sidebar's Pinned section, and on phones, which have no sidebar, in a compact strip at the top of Home (`PinnedStrip`). Status, pin and order writes are optimistic (`useOptimisticMutation`) and roll back on refusal.
- View choices live in `localStorage` through `application/preferences` (`wheelhouse.show-inactive`, `wheelhouse.sidebar-collapsed`, `wheelhouse.environment`, `wheelhouse.products-view`, `wheelhouse.products-collapsed-workspaces`, `wheelhouse.last-product`), every access wrapped so blocked storage only loses the choice. Icon addresses the host answered not found are remembered for 12 hours (`wheelhouse.missing-icons`, `application/products/IconAvailability.ts`), so each mark falls back to its tinted letter without asking again; Refresh from repository forgets a product's entries.
- First load: every page is a lazy route chunk; Vue with its router and the query cache with zod ship as `vendor-vue` and `vendor-data` chunks beside the entry (`vite.config.ts`). Shell parts a first visit rarely needs load on first use — the phone's profile sheet, the tablet's drawer and the pin editor — as do the product page's tabs other than Overview, and barrels that carry heavy modules (`presentation/products` without `RepositoryActions`, `presentation/pins` without `PinEditor`) are bypassed by path in the shell.
- The product form's Deployed by picker edits the product's deploy mode (Wheelhouse, its own CI, nothing; `ProductDeploy`). Only a product Wheelhouse deploys takes automatic deploys: for the others the Deploys section's switches stay off and locked (`automationLockOf`), and saving a product refreshes the automation and history views, since its mode decides what Ready to promote offers.
- Registry/runner association uses explicit bindings in `application/product/ProductInventory.ts`. Product status, observed runtime condition and deployment outcome remain separate facts; per-environment health on the product cards (Products page and Home) comes from `domain/overview/EnvironmentHealth.ts` over the targets and vitals the console already reads.
- The Products page (`presentation/products/pages/ProductsPage.vue`): one filter row (`ProductFilters`: search by name, slug or description; workspaces, a red mark on one whose products fail; status — failing, needs a look, healthy, not deployed; the date range — the Deployments page's `DateRangeFilter`, 90 days by default; the one Show inactive switch; sort — name by default, last deployed, oldest updated, failed first, succeeded first; on phones a search and one Filter sheet that holds the range and sorts too), kept in the address (`q`, `workspace`, `status`, `range` or `from`+`to` as the Deployments page writes them, `sort`; `domain/portfolio/ProductFilter.ts`), defaults left out. The filter governs both sections alike: search, workspaces and status decide which workspaces and products show (narrowed, only workspaces with a match), and the range sets the period their figures and trends cover. Then Workspaces — a card or row each with its product count and its figures over the products it shows (`workspaceStatsOf`): compact pills in the status vocabulary's icons and tones (`WorkspaceStatPills`) — rollouts that succeeded over the range with the success rate folded in (`✓ 40 · 95%`), then products failing, degraded and deploying now, a zero left out — beside the range's rollouts as a chart (`WorkspaceTrend`), succeeded in a quiet neutral with failures red above, a column a day up to a month, a week up to about six months, a month beyond (`RolloutBuckets`), on its own scale; one line as on a product card, the chart taking the room the pills leave (up to 7rem). The figures come from one read of `/api/deployments/history/activity` per card over the shown products (`useWorkspaceActivity`, under the history views' key, read every minute, the previous figures held while a new filter loads). A click scrolls to its group (a sideways strip of cards on phones) — then the products grouped by workspace in custom order under a minimal fold-away separator (name, count; folding remembered). One Cards | Rows switch in the top bar governs both sections from `md` (`wheelhouse.products-view`); phones always show full-width cards. A product card: mark, name (pin and manifest-problem marks), two-line description, the open-site control (one address opens directly; several list each front-facing site with dev and prod buttons, private ones locked) and the overflow menu (Repository, Edit product, Pin, Mark inactive — never Promote, which lives on the Deployments page), then one pill per environment and the deploy trend. Pills (`EnvironmentPill`, rules in `domain/portfolio/EnvironmentPill.ts`) are outlined: status icon, environment and the serving version when calm, or the state word — healthy is neutral with only the check green; failed red; degraded amber — rolled back to the previous release, or restarts or host pressure, the details naming the cause (`rolled back to v1.2.0`); deploying blue; no target and nothing deployed are one dashed state; a product whose stored deploy mode is `ci` and that has no target here shows a workflow icon (`EnvironmentPillRules.ciOf`), and the console's own product (`ConsoleProduct`) the version this console runs in the environment it serves (`/api/system/status` `environment`); no reading is neutral. Hovering or focusing a pill opens its details (the cause, release serving, latest rollout's release, status, time and actor, why it failed). Pills read health from targets and vitals without deployment stats; the portfolio summary (`GET /api/portfolio/summary`, read every minute under the history views' query key) carries each environment's latest and serving rollouts and weekly counts. Trends (`WeeklyBars`, a local SVG — the fe sdk `Sparkline` draws one series): a product's finished rollouts per week over every week the range touches (`TrendWindows`: the summary read again with its `weeks` and, for a past range, its `to`; Home keeps 12 weeks to now), prod from the baseline and dev above in two validated hues (`--color-chart-prod`, `--color-chart-dev`), one scale shared by every product on the page so busy and quiet products compare, nothing for a product never deployed. Pills always read as of now, whatever the range. The pill legend, how to read a trend and what a workspace card counts sit behind the info button beside the Products heading (`ProductsInfo`).
- Home (`presentation/home/pages/HomePage.vue`): Needs attention while something does, then every workspace in custom order (its name opens its group on the Products page) with its products as the Products page draws them — `ProductTile`: pills, trend, open-site and overflow menus, Edit opening the product form, loaded on first use — over `useProductFacts` at 12 weeks to now. Pins live in the sidebar, so Home shows them only on phones, as a compact strip of chips at the top (`PinnedStrip`, below `md`, with Edit for reordering), until the Home widgets analysis lands.
- Servers list the products each hosts (`hostedProductsOf`, from the targets) and lead with degraded ones: a server that cannot be read, is overloaded, short on memory or nearly out of disk (`AttentionRules.ofServer`) names what is wrong and the products it affects, each linking to its page. A vault row opens the Secrets page on that vault (`vaultLocation`).
- Host vitals are current snapshots that the SDK query refetches every 60 seconds; each server's host history comes from the backend sampler, which keeps samples for its retention window. Deployment follow-up refetches every three seconds while the tab is visible.
- The Deployments page, top to bottom: Issues (`IssuesPanel` over `/api/deployments/issues`: each target whose latest rollout failed, rolled back, failed to roll back or was interrupted with no success since, and each rollout stuck over 30 minutes — product, environment, release, what happened, when and by which actor; Open, Redeploy, or Reconcile where the target is likely locked, which first reads the target's state and opens `ReconcileModal` on the remote rollout it reports; read every minute while visible; absent when there is none), Running now (live rollouts, their step and a ticking elapsed time; read every three seconds while visible, absent when nothing runs; a rollout leaving the list refreshes the history views) and Ready to promote (one Promote per product opens the deploy dialog on its prod target and release; each row shows the release's dev check as a status pill — passed, failed, not run, no check declared; `DevCheckRules`, `DevCheckPill` — and says when it holds auto-promote, as do the prod confirm step and the fleet confirm, which warns before promoting an unchecked release; inactive products hidden; absent when nothing waits), all three portfolio-wide whatever the filter; then the filter (`DeploymentFilterScope`: the page's one `DeploymentFilterBar` in a glass strip that sticks under the top bar; its reach and which attempts show sit behind its info button), the four measures (`RangeStatsTiles`: deploys, success rate, median rollout and recovery against the range before; entities and range, following the All attempts toggle as the records do), and `DeploymentsPanel`, which holds a filter bar of its own, with the four measures as inset tiles under it, only on a product's Deployments tab. The filter bar: `EntityPicker` (a Workspace → Product → Service checkbox tree, mix and match, summarized as chips; `domain/deployments/history/EntitySelection.ts`), the All attempts toggle (below) and `DateRangeFilter` (24 h to 12 months, or custom local from/to); both pickers are popovers from `md` and bottom sheets on phones. Filter, view and expanded day live in the query (`workspace`, `product`, `service`, `range` or `from`+`to`, `view=list`, `day`; `application/deployments/DeploymentFilterQuery.ts`), defaults left out; the status filter is gone (decision 42), so an old link's `status` is ignored and the next write drops it. Grid (`ActivityGrid`, rules in `ActivityCalendar.ts`): week columns × Monday-first weekday rows over the range (six months by default), fixed 20px cells with 4px gaps (22px with 3px gaps on phones), the calendar only as wide as its weeks, a day taking the loudest attention of its applied, finished deploys — each target's last of the day, so a failure fixed later that day leaves it green, or every attempt while the toggle shows them, when a mixed day (one needing nothing beside one needing a look or action) is split diagonally, its lower-right half in the calm fill — green when none needs anything, amber with a half-dot when one is worth a look, red with a cross when one needs action — four fill steps (1, 2–3, 4–6, 7+), a deploy that changed nothing never colouring a day, one shared tooltip drawn in the top layer (teleported to `body`) and kept inside the viewport — above its cell, below at the top edge, slid in at the sides (`HintPlacement`) — so no panel or screen edge clips it, and an aria-label per day, arrow keys between days, today in a dashed ring of the muted foreground tone (pulsing while a rollout runs, still under reduced motion) and the chosen day in a solid primary ring set off from the cell — chosen today keeps the solid ring and adds a small today dot; a compact key sits behind the info button beside the panel's title (`DeploymentsInfo`: four short lines — a square per day, the three colours as swatches, what All attempts changes, choosing a day and the arrow keys — and in the List view the statuses with the same attempts line), and nothing under the calendar repeats the measures; phones scroll it sideways from the newest weeks with sticky weekday labels. From `lg`, when the panel has room beside the calendar (`SidePanelRoom`, measured), a day panel sits to its right; narrower, it stacks beneath the calendar, the same panel either way. Its header is the date (the year left out in the current one) with a today tag, its info button (how to read the rows, then the statuses' legend) and Close (icon-only on phones), over the day's counts (`DeploymentDayStats`: an icon and a number per state that occurred, the icon in the loudest attention among them, each word in its title and for assistive technology, a trailing `+` while older ones remain; `DeploymentStates.counts` over the day's deployments, read 100 a page). Below it, one compact row per product (`DayProductRows`, rules in `DayLanes`): the product's name (wrapping to two lines between words, never inside one: a word too long for the column ends in an ellipsis, the whole name in its title; a lane narrows, its glyphs wrapping, before the name drops below 7rem), then a lane per environment — dev and prod always, any other the day reached after them — holding the environment's last deploy that day (one per server), what it runs now, or, while the toggle shows every attempt, one glyph per deploy, oldest to newest: the state's icon in its attention's colour, dashed when it changed nothing, a same-day failure kept as it is. A lane fits two to four glyphs a line by the day's busiest lane (three on a phone, 26px glyphs) and wraps beyond. A thin left-edge bar marks a row whose lanes' latest deploys need action (red) or a look (amber) — a later deploy that changed nothing never hides a failure, though one needing a look raises a calm lane — and those rows lead, then the rest, by name. Pointing at or focusing a glyph shows `version · time · state · actor` (and `on {server}` where the product runs that environment on several servers) in a tooltip drawn in the top layer (`HintPlacement`); on touch a tap shows it with an Open the release link, closed by a tap outside or Escape. A click opens the release: the product page's Deployments tab as a list over the view's range with `release` and `env` in the address (`releaseLocation`, `/p/{product}/deployments?view=list&release=v1.2.3&env=prod`), whose list marks that release's rows in that environment, reads older pages until it finds them (up to 20), scrolls to the first, and offers a chip to clear the choice; a deploy whose product is gone opens its own page. Causes, service strips and actions stay in that list and on the deployment's page, never in the day panel. With no day chosen, the side shows one line asking for a day, so choosing one never shifts the layout. List rows load older pages behind Load older. The calendar, the day panel, the list and the four measures take each target's latest deploy of a local day (decision 42): the API's `latest=true&tz=` selection (`DeploymentQuerying.Select`, the stats' `Counted`), so the earlier attempts that day and the deploys that changed nothing (Not applied: refused, replaced in the queue, cancelled, expired, a failed check before changes) stay out until the viewer's one toggle shows every attempt: `AttemptsToggle` "All attempts" in the filter bar between the entity picker and the range, an eye-off icon, its name (folded away on phones, leaving the icon and the badge, so a product tab's toggle and range keep one line, the range's label truncating) and a badge with the count of hidden attempts (the measures' `notApplied` plus `superseded` for the filter's products and range, which the API reports whatever the toggle), pressed while showing, its one line in its tooltip above it ("N earlier or unchanged attempts hidden — show every attempt") and in the filter's info button on touch; `wheelhouse.show-all-attempts` remembers it, off by default, outside the address, and every history read (`useDeploymentPages`, `useDeploymentActivity`, `useDeploymentRangeStats`; `useHistoryView`) sends `notApplied=true` while it is on and `latest=true` while it is off, with the owner's `tz` — the product's Deployments tab included. The Issues panel is unchanged. `/deployments/:id` (`DeploymentDetailPage`) reads in the status design's order: the state chip with when changes started and stopped, what the environment runs now (`DeploymentStates.nowRuns`, `prod now runs two releases`) with each service's glyph, version and result, the facts; Cause and effects (the origin, each effect likely via it along a declared path — never an observed call — and what a roll back restored or could not); the rollout steps split at "Changes start here" (`DeploymentStates.sections`, roll back steps nested); the services table (versions from → to → back, the result with the origin ringed and why it changed — image, config, settings, added — and its health); then Impact (`ImpactList`: the origin, its effects indented, then any other service not fine, with Open map onto the product's service map at the origin) — under the header on phones, beside the page from `lg` — sites, snapshot and links. The header's actions fit the state: Partial and Failed reconcile (when the target reports it needs it), Rolled back redeploys, Not applied retries; Roll back and Read logs as before.
- Context a region needs once — its legend, what a control applies to, its gestures, the period and units of its figures — sits behind an info button right after the title it explains, outside the heading (`presentation/common/components/InfoPopover`; a `Panel` takes it in its `info` slot; rules in `wow-two-ws/conventions/development/frontend/core/mla/domains/guidance/guidance.md`); a panel subtitle that was pure context moved there (Environments, Services and its map legend and gestures, Ready to promote, Releases and builds, Environment bindings, a vault, Actions, a deployment's Sites and Snapshot, the inspector's notes). It opens on click only — a popover from `md` on the side with room, its height capped there and scrolling inside, a bottom sheet on phones — and never by itself: a guided first-visit tour is a separate future feature (backlog) with its own text and spotlight. The button is dimmed; where the device hovers with a fine pointer it stays hidden (opacity only, so it stays in the tab order) until the pointer or focus is inside its region, the nearest `data-info-scope` ancestor — a `Panel` declares itself; on touch devices (no hover, or a coarse pointer) it always shows, dimmed, since nothing hovers there.
- One status vocabulary (`domain/common/StatusVocabulary.ts`: states, words, tones; `presentation/common/components/StatusStyles.ts`: icons and classes; `StatusPill`) draws every pill, mark and count. An environment's states: healthy calm (neutral, green icon), deploying blue, failed red, degraded amber (a roll back, a regression, restarts or host pressure, the details naming the cause), mixed red (a partial rollout: `2/3 on 0.4.0`), no reading quiet, nothing deployed dashed, CI calm with a workflow icon; at most one corner marker — a cross when the last attempt changed nothing but needs a look (`lastAttempt`), a clock while a deploy waits, an eye while the serving release is watched (`EnvironmentPillRules`). A deployment reads in eight states from the API (`state`, `substate`, `attention`, `cause`, `effects`, `services` on every item): In progress, Succeeded, Degraded, Rolled back, Partial, Failed, Not applied, Unknown — the icon says what happened, the colour the attention it needs (none, info, look, act, muted), the word both; Not applied wears a dashed outline and Unknown a dotted one (`DeploymentStates`, `domain/deployments/DeploymentStatus.ts`). One chip draws it everywhere (`DeploymentStateChip`: icon, word, `· sub-state`, optionally the cause on a second line with its kind's icon), and `DeploymentStatusPill` reads a runner status alone the old way for reads that carry no state; the service strip (`ServiceStrip`) puts one glyph per service in rollout order beside it, the origin ringed, in words on phones (`2 of 3 updated`).
- The Catalog page (`/settings/catalog`) groups the `catalog.yml` apps by workspace (`CatalogWorkspacePanel`, `CatalogRules.groups`): each panel names the workspace (New when Wheelhouse lacks it), counts its apps importable, in Wheelhouse and not deployable, and offers Select all importable and Import workspace; the top bar's Import takes the selection across workspaces. Every import posts `POST /api/catalog/import {slugs}`.
- Deployments submit approved target/release IDs. Reconciliation submits the authoritative remote active rollout ID and requires exact typed target confirmation. API action headers remain explicit.
- One SDK auth bridge (`sessionBridge` in `integration/common/client.ts`, keyed by the GitHub login) owns the session: its scope runs the HTTP client and the query client, so a sign-in, a sign-out or an expiry cancels the previous session's requests and clears its records. `useAuth` publishes the `me` read (authenticated or anonymous) and anonymous on sign-out. A signed-in session's first 401 expires it once (`subscribeExpired`): one neutral "Signed out — sign in again" notice, never an error toast per 401, and `App.vue` shows the sign-in screen in place, so the address stays; sign-in returns to its path and query (`authApi.signInUrl`), keeping `?env=` and `?item=`.
